## 0. The problem, in one line

Every engine in Code mode ends a turn when its model stops talking, and the person
sitting at the desktop is the one who types "continue". On a task with fifty steps
the owner becomes the scheduler of the system. The Run makes the desktop continue the
turns by itself, stop only where a human is actually needed, and show everything it
decided.

## 1. Where a turn ends today — the eight answers

🔬 All rows were read in the code on 10/09/2026 (SHVIA-DESKTOP 1.4.37, SHVIA-WEB
2.110.234, SHVIA-CODE 0.11.20).

| # | Question | Answer in the code |
|---|---|---|
| 1 | How is the session kept | One sidecar per **window** (`Sidecars` map in `code_bridge.rs`, keyed by window label). The Claude runner creates one `query()` per turn and passes the SDK session id in `resume` |
| 2 | Can the host send a message programmatically | Yes: one NDJSON line on the sidecar's stdin (`Sidecars::send_line`). The web page also keeps its own queue (`codeQueue`, drained on `turn_done`) |
| 3 | How streaming works | SDK → runner NDJSON → bridge `_emit` → `code-mode.js`. A long answer is checkpointed to the server every 3 s while it streams (`CHECKPOINT_MS`, PR #80) |
| 4 | When the turn is over | Claude: the SDK `result` message → `turn_done` (`claude-runner.mjs:388`). Codex: `turn/completed` → `turn_done`. anna: the model returns no tool call → `turn_end` |
| 5 | Where it is persisted | `code_turns` in SHVIA-WEB, per user and project, kinds `user`, `assistant`, `boundary`. A reading record: nothing goes back to an agent |
| 6 | Identity | `folders.id` (the project) + the folder path bound on this machine. There is no run entity |
| 7 | Survives a restart | The transcript does; the agent's context does not. The runner keeps `sessionId` in memory only and a respawn never passes `resume` — that is the `boundary` line the timeline draws |
| 8 | Tied to an HTTP request or to a queue | Neither: tied to the desktop process. The server is the inference for the gateway engine (key, audit, `ToolLoopGuard`) but has no files and runs no tools |

🔴 **A finding that any orchestrator would inherit.** The Claude runner only emits
`error` when the SDK `result` carries `subtype === "error"` (`claude-runner.mjs:385`).
📋 In the pinned SDK (`@anthropic-ai/claude-agent-sdk` 0.3.258) that subtype does not
exist on a `result`: the real ones are `error_during_execution`, `error_max_turns`,
`error_max_budget_usd`, `error_max_structured_output_retries`, and `success` with
`is_error: true`. Today a turn that dies on an API error ends the timeline as `usage`
+ `turn_done`, with no error line. With `maxTurns` and `maxBudgetUsd` in play, a cap
would be silent too, and a CONTINUE decision would be taken on a turn that had just
hit its ceiling. This is block B0.

## 3. Decisions

The record with context and alternatives is ADR-034. The list, so this document
reads alone:

- **D1 — The Run is a posture of the turn, not a mode.** Like "Confiar" is a posture of
  the project. The screen gains one control, one bar and three timeline pieces.
- **D2 — Two axes, two pills.** *Autonomia* says whether the **turn** continues by
  itself. *Aprovação* says whether a **tool** runs by itself. A run under Aprovação
  Manual continues its turns and still asks a card for every write.
- **D3 — Three tiers, in this order.** Rule (no model): a progress report continues; an
  irreversible action goes to the human. Orchestrator with a model: when the rule says
  ASK, a model reads objective + plan + assumptions + the last message and answers
  CONTINUE-with-a-message or ASK_HUMAN. Human: whatever the tiers above do not resolve.
- **D4 — The orchestrator is a gateway profile, not an engine.** `modelo@servidor` from
  the catalogue, with "Rule, no model" as option zero and a different family than the
  coder as the default when a model is chosen. Its calls are audited in
  `inference_requests` even when the coder runs outside the gateway.
- **D5 — The decision is made by the server and carried by the page; the runner stays
  credential-free.** The Claude runner receives no ShvIA key on purpose
  (`code_bridge.rs`, the `is_claude` branch of `spawn`), so its `Stop` hook cannot call
  the gateway. It emits a blocking `stop_request` on NDJSON, the page calls
  `POST /api/v1/code/orchestrate`, and answers by `id`. For anna and Codex the page
  makes the same call at `turn_done`. One orchestrator, three engines.
- **D6 — Artifact contract.** The orchestrator receives objective, plan, assumptions and
  the last message. Never the transcript.
- **D7 — Guards that are code, not prompt.** Irreversible never reaches a model. A
  timeout of the orchestrator falls back to the rule, and the rule in ASK goes to the
  human: errs toward the alarm. The runner's own ceiling on a `stop_request` with no
  answer ends the turn normally, so a closed page never hangs a turn.
- **D8 — Every decision names its decider and is persisted.** Rule, the profile, or you:
  in the continuation line, in the panel's decisions list and in the summary, and as
  `code_turns` rows. `ASSUMPTIONS.md` becomes that list.
- **D9 — Desktop-only, explicitly.** Closing the desktop ends the run. What survives the
  machine is a mission in `SHVIA-WORKSPACE`; the bridge from the Code mode "+" to the
  workspace is a separate front (`REPOSITORIO-NO-WORKSPACE.md`, decided 19/08).
- **D10 — Caps from the first version.** Iterations and cost, with Pausar and Parar on
  the bar. On the Claude engine the caps are also passed to the SDK (`maxTurns`,
  `maxBudgetUsd`); on the others the page counts.

## 4. Contracts

Everything in this section is a **proposal** of shape. Names may change in the block
that implements them; what must not change is who holds which responsibility (D5).

### 4.1 NDJSON — `stop_request` (engine → host) and its answer (host → engine)

An addition to `SHVIA-CODE/docs/embedding.md`, optional per engine: only an engine that
can **hold a turn open** emits it. Today that is the Claude runner. anna and Codex never
emit it; their continuation is between turns.

```
engine → host   {"type":"stop_request","id":"s-7","iteration":7,
                 "last":"Etapa 1 concluída… Posso seguir para a API?",
                 "reason":"model_stopped"}                        (BLOCKS)
host → engine   {"id":"s-7","decision":"continue","message":"Continue conforme o plano. Não peça confirmação entre etapas."}
             |  {"id":"s-7","decision":"stop"}
```

- `last` is the last assistant text, cut at 4.000 characters; the page already has the
  full text in the timeline.
- `iteration` is the runner's count of stop requests in this turn's query, so the page
  can correlate with its own count.
- stdin closed with a `stop_request` pending → `stop` (the same safe default the gates
  use: reject).
- The runner keeps a ceiling of 60 s per `stop_request`: no answer → `stop`. The turn
  then ends as it does today, and the page can still continue between turns.
- `decision: "continue"` becomes the hook output `{decision:'block', reason: message}`;
  `stop` becomes an empty output (let the turn end).

### 4.2 Server — `POST /api/v1/code/orchestrate`

Stateless, like `/code/chat`. Same auth guard and the `code:chat` token ability
(question Q4 in §8). No tools, no history.

Request:

```jsonc
{
  "engine": "claude",                    // claude | codex | gateway
  "orchestrator": "rule",                // "rule" | "modelo@servidor"
  "objective": "Implementa o módulo Markdown…",
  "plan": "1. migration… 5. conflito",   // optional, the coder's own plan if it wrote one
  "assumptions": ["(b) manter as duas colunas…"],
  "last_message": "Etapa 1 concluída… Posso seguir?",
  "policy": { "ask": "stop", "irreversible": "stop" },   // v1: both fixed to stop
  "run": { "iteration": 7, "max_iterations": 100, "cost_usd": 0.84, "max_cost_usd": 5 }
}
```

Response:

```jsonc
{
  "decision": "CONTINUE",               // CONTINUE | ASK_HUMAN | DONE | STOP
  "message": "Continue conforme o plano. Não peça confirmação entre etapas.",
  "reason": "relato de etapa com pedido de confirmação",
  "signal": "pergunta-retorica",         // the classifier's signal, or the model's label
  "decided_by": "rule",                  // "rule" | "modelo@servidor" | "cap"
  "elapsed_ms": 41
}
```

Tiers inside the endpoint, in order, each one able to answer alone:

1. **Caps** (`run`): iteration or cost at the ceiling → `STOP`, `decided_by: "cap"`.
2. **Markers**, deterministic: the execution contract (§4.5) asks the coder to end with
   `RUN_DONE: <one line>` when finished and `NEEDS_INPUT: <what>` when only the human
   can answer. `RUN_DONE` → `DONE`; `NEEDS_INPUT` → `ASK_HUMAN`. Same marker the
   workspace missions already use.
3. **Rule**: the port of `classificador.py` (signals and the irreversible list) to
   `App\Services\AI\RunOrchestrator`, a pure class. DOC → `CONTINUE`; `fecho` without a
   next step → `DONE`; ASK → tier 4 or `ASK_HUMAN`; irreversible → `ASK_HUMAN` always.
4. **Model** (only when `orchestrator` is a profile and the rule said ASK): one call
   through `ChatService` with a JSON schema answer, `temperature 0`, timeout 20 s,
   audited with `origin = code-orch`. Any failure → `ASK_HUMAN` with
   `decided_by: "rule"`.

🔴 The rule tier's tests use a corpus labelled by a signal **independent** of the one
under test, and a reviewer who did not write it tries to break it before it ships. Both
are lessons the house recorded on 08/09 (`.continue/EXPERIMENTO-IDIOMA-DO-ASSUNTO-20260908.md`
in SHVIA-WEB).

### 4.3 The page — the run state machine (`code-run.js`, pure)

| State | Meaning | Leaves on |
|---|---|---|
| `off` | Autonomia = "Um turno" | pill → "Até terminar" ⇒ `armed` |
| `armed` | "Até terminar" selected, no turn in flight | send ⇒ `running` |
| `running` | a turn is in flight | `stop_request` ⇒ `deciding` · `turn_done` ⇒ `deciding` · Pausar ⇒ `pausing` · Parar ⇒ `stopped` · `error` ⇒ `failed` |
| `deciding` | `/orchestrate` in flight (turn held open, or between turns) | `CONTINUE` ⇒ `running` (answer the `stop_request`, or push "continue" into `codeQueue`) · `ASK_HUMAN` ⇒ `waiting_human` · `DONE` ⇒ `done` · `STOP` ⇒ `failed` (cap) · timeout ⇒ `waiting_human` |
| `waiting_human` | the gate card is on screen | user sends ⇒ `running` · Encerrar ⇒ `stopped` |
| `pausing` | Pausar pressed; holds at the next `turn_done` | `turn_done` ⇒ `paused` |
| `paused` | nothing in flight; counters kept | Retomar ⇒ `deciding` · Parar ⇒ `stopped` |
| `done` / `stopped` / `failed` | terminal for this run; the session stays alive | send ⇒ a normal turn (`off` or `armed`, per the pill) |

The engine only changes **where** `deciding` is entered: from `stop_request` on Claude,
from `turn_done` on anna and Codex.

A user message typed during `running` goes to `codeQueue` as today and is delivered at
the next `turn_done`; it does not change the state.

### 4.4 Persistence — `code_turns`

Two new kinds, alongside `user`, `assistant`, `boundary`:

| kind | content | model | when |
|---|---|---|---|
| `run` | JSON: `{event:'start'|'end', outcome, iterations, decisions_auto, decisions_human, cost_usd, tokens, duration_s, caps}` | the orchestrator id | start and end of a run |
| `decision` | the reason line as shown on screen (`"continuou · relato de etapa · regra"`) | `decided_by` | every orchestrator decision |

The client writes them through the existing outbox (idempotent by `client_id`); the
timeline restore renders `decision` as the continuation line and `run` as the summary
card. The Histórico tab groups by run (block B7).

### 4.5 The execution contract

The first user message of a run carries a fixed preamble, the same for the three
engines, rendered from the pill's values:

```
Trabalhe até terminar. Não pare para relatar progresso nem para pedir confirmação
entre etapas: registre o progresso no próprio trabalho. Pare só quando:
1. terminar — encerre com uma linha `RUN_DONE: <o que foi entregue>`;
2. só eu puder responder (decisão de produto, credencial, dado que você não alcança)
   — encerre com `NEEDS_INPUT: <o que falta>`;
3. a próxima ação for irreversível e não estiver prevista.
Teto desta run: 100 iterações, US$ 5,00.
```

It is an instruction, and the house knows instruction alone does not fix what failed
three times (`.continue/estado-atual.md`): the markers make the deterministic tier
cheap, and the rule and the guards hold when the model ignores the contract.

## 5. Per engine

| Engine | Where `deciding` is entered | Cost of one continue | Caps enforced by |
|---|---|---|---|
| Claude Code | `stop_request` inside the turn; on CONTINUE the model keeps its context | near zero, no new turn | SDK (`maxTurns`, `maxBudgetUsd`) and the page |
| SHVIA (anna) | `turn_done`; on CONTINUE the page pushes "continue" into `codeQueue` | one full turn | the page (anna's own 100-round cap is per turn, unchanged) |
| Codex | `turn_done`, same as anna; `codex app-server` has no hook surface | one full turn | the page |

The decider is the same in the three: the rule, or the orchestrator profile chosen on
the gateway, always called by the page, never by the runner.
