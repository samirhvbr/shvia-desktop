## 1. Objetivo

Adicionar ao ShvIA Desktop um **Modo Code**: uma segunda face do app, no estilo
Claude Code, onde o usuário seleciona um projeto vinculado a uma **pasta física
local** e a Anna atua como agente de código sobre essa pasta — lê arquivos,
propõe edições com diff, propõe comandos, roda testes — sempre com aprovação
humana antes de tocar disco ou executar qualquer coisa.

O modo Chat atual permanece intocado. O Modo Code é uma visão alternativa do
mesmo app, alternável a qualquer momento.

## 2. Tese arquitetural

**O ShvIA Desktop é a casca visual; o `anna` é o motor.**

O trabalho recente no `anna` (`--json`, perfis de ferramenta, arco 0.5.1–0.5.3)
foi construído exatamente para este caso: uma casca local que quer o **loop
agêntico completo** com `read_file`, `edit_file` com diff, `grep`, `git` e
`bash`. O SShvTerm não era esse caso — ele já tinha loop de host próprio, por
isso lá a solução foi o provider nativo (`shvia_code`) no sidecar Python. O
Modo Code do ShvIA Desktop **é** o caso do `--json`.

Consequências:

1. O app spawna `anna --json` como **sidecar** com `cwd` na pasta do projeto.
2. Os eventos NDJSON do `anna` viram a timeline (leituras colapsadas, diffs
   como cards, texto streamando); as aprovações voltam pelo stdin.
3. A inferência continua passando pelo **gateway** com a chave do usuário —
   auditoria, contagem de tokens e o medidor "Uso de API hoje" funcionam sem
   trabalho adicional.
4. **Nada de loop server-side** para este modo: os arquivos estão na máquina
   do usuário; um loop no Laravel exigiria reimplementar um executor local de
   tools no app de qualquer jeito (o problema do SShvTerm, invertido).
5. **Nada de reimplementar tools no app**: o app só renderiza e aprova.

Perfil de ferramentas: o Modo Code usa o **perfil completo/local** do `anna`
(`read_file`, `edit_file`, `grep`, `git`, `bash`). O perfil `--tools host`
(só `bash`) permanece exclusivo do caso SShvTerm.

## 3. Não-objetivos (v1)

- Versão web/browser do Modo Code (exige FS local → desktop only).
- Multi-abas / múltiplas sessões simultâneas por projeto.
- Painel de terminal dedicado (saída de comandos é inline nos cards).
- Substituir a aba Agente do SShvTerm (casos distintos, coexistem).
- Mudanças no backend Laravel ou no `/api/v1/code/chat` (nada obrigatório).
- Sincronização de sessões code com o banco (fica pra v2 — ver D5).
- Editor de texto embutido (o agente edita; o humano revisa via diff).

## 4. Arquitetura

```
┌──────────────────────────── ShvIA Desktop ────────────────────────────┐
│  Modo Chat (atual, intocado)      Modo Code (novo)                    │
│                                   ├─ timeline (cards, aprovação)      │
│                                   ├─ painel da pasta (git, árvore)    │
│                                   └─ config local projeto→pasta       │
│                                          │ spawn (cwd = pasta)        │
│                                          ▼                            │
│                                   anna --json  (sidecar)              │
│                                   ├─ loop agêntico + tools locais     │
│                                   ├─ stdout: eventos NDJSON           │
│                                   └─ stdin: aprovações/mensagens      │
└──────────────────────────────────────────│────────────────────────────┘
                                           ▼  HTTPS + chave do usuário
                                    Gateway ShvIA (Laravel)
                                    ├─ auditoria / tokens / quotas
                                    └─ Ollama local | provedores nuvem
```

### 4.1 Ciclo de vida do sidecar

- **Spawn:** na primeira mensagem da sessão (não ao entrar no modo — evita
  processo ocioso). `cwd` = pasta do projeto. Um processo por sessão ativa.
- **Encerramento:** trocar de projeto, sair do Modo Code ou fechar o app →
  SIGTERM com timeout de 5 s → SIGKILL. PID registrado em pidfile do app;
  na inicialização, o app mata `anna` órfãos do próprio pidfile.
- **Crash:** card de erro na timeline + botão "Reiniciar sessão".
- **Logs:** stderr do `anna` → log rotacionado do app (nunca na timeline).
- **Ambiente:** chave de API do usuário e URL do gateway repassadas conforme
  o mecanismo real de autenticação do `anna` (ver P4); seleção de
  infra/modelo do header repassada por flag (ver P5).

## 5. Contrato de eventos — alvo (validar na F0)

A tabela abaixo define **o que a UI precisa**, não o que o `anna` já emite.
Os nomes reais dos eventos, campos e o protocolo de aprovação **devem ser
extraídos do código do `anna` na F0** — nada de ouvido. Onde faltar
capacidade, ela vira item da F1.

| Necessidade da UI                       | Evento alvo (placeholder)                     | Render |
|-----------------------------------------|-----------------------------------------------|--------|
| Início/fim de turno                     | `turn_start` / `turn_end`                     | estado do composer |
| Texto do assistente streamando          | `text_delta {text}`                           | parágrafo da timeline |
| Tool read-only executada                | `tool {name, args}` (read_file/grep/git-ro)   | linha discreta colapsável |
| Proposta de edição                      | `edit_proposal {id, path, diff}`              | card de diff + Aprovar/Rejeitar |
| Proposta de comando                     | `command_proposal {id, command, why}`         | card de comando + Rodar/Rejeitar |
| Resultado de comando                    | `command_result {id, exit_code, output}`      | corpo do card (colapsado) |
| Resultado de edição aplicada            | `edit_result {id, ok}`                        | badge do card |
| Métricas do turno                       | `usage {tokens, elapsed_ms, model, server}`   | rodapé de métricas |
| Erro                                    | `error {message}`                             | card de erro |
| **Resposta de aprovação (app → anna)**  | stdin: `{id, decision: approve\|reject}`      | — |

Requisito duro do protocolo: propostas carregam `id` correlacionável e o
`anna` **bloqueia** aguardando a decisão daquele `id` — sem isso o
propose-approve não existe.

## 6. Vínculo projeto → pasta

- O vínculo é um **caminho local**, portanto mora na **config do dispositivo**
  (arquivo de config do app), chaveado pelo `project_id` do backend. O mesmo
  projeto pode apontar para pastas diferentes em máquinas diferentes. Nada
  disso vai para o banco na v1 (ver D3).
- Projeto sem vínculo, no Modo Code, mostra estado vazio com CTA
  **"Vincular pasta do projeto"** (file picker nativo).
- Caminho vinculado que deixou de existir → estado de erro com "Revincular".
- **Nomenclatura:** na UI é sempre **"Pasta do projeto"**. Nunca "workspace"
  nem "pasta de trabalho" — esses nomes já são o conceito de pastas de upload
  server-side no Laravel (`WORKSPACES.md`) e a colisão confunde.

## 7. UI e layout

Referência canônica: `docs/mockups/modo-code-mockup.html`. Design system
vigente: canvas `#0e0e10`, acento terracota `#c87f5a`, Montserrat, princípio
"remover antes de adicionar". Nenhum token novo.

### 7.1 Entrada no modo

- **Segmento `Chat | Code`** no header, ao lado esquerdo dos seletores — o
  modo fica visível o tempo todo e a troca é um clique (recomendação da D1).
- Menu **Ver → Modo Code / Modo Chat** como acelerador, com atalho
  (sugestão: `Ctrl+1` Chat, `Ctrl+2` Code — confirmar conflitos na F2).
- Alternar de modo **não** destrói estado: o chat continua onde estava e a
  sessão code idem.

### 7.2 Coluna 1 — sidebar global (muda pouco)

- Lista de projetos igual à atual; projetos **com pasta vinculada** ganham
  ícone de pasta e, quando ativos no Modo Code, o caminho como subtítulo.
- "Novo bate-papo" vira **"Nova sessão"** quando o modo ativo é Code.
- Busca, uso de API e conta permanecem como estão.

### 7.3 Coluna 2 — painel da pasta (substitui instruções/fontes/conectores)

Seções, nesta ordem:

1. **Pasta do projeto** — caminho em mono + ação de revincular no overflow.
2. **Git** — branch atual + contagem de alterados + lista curta de arquivos
   com status (`M`/`A`/`D`). Fonte: `git status --porcelain -b` executado
   **pelo app, read-only** (não pelo `anna`). Sem repo git → seção oculta.
3. **Arquivos** — árvore da pasta, profundidade inicial 2, lazy-load ao
   expandir; ponto terracota nos arquivos tocados na sessão. Ignora
   `.git/`, `node_modules/`, `vendor/`, `target/` por padrão.
4. **Sessões** — sessões code anteriores deste projeto (ver D5), a ativa
   destacada.

### 7.4 Coluna 3 — timeline do agente

Elementos e estados:

- **Mensagem do usuário:** balão alinhado à direita (igual ao chat).
- **Linha discreta (tools read-only):** ícone + `nome args` em mono, 1 linha,
  colapsada; clique expande o resultado.
- **Card de diff (`edit_file`):**
  - Cabeçalho: ícone + `edit_file <path>` + badge de estado.
  - Corpo: diff unificado com fundos verde/vermelho translúcidos; render
    truncado acima de ~2 000 linhas com "expandir" (aplicação não é afetada).
  - Estados: `aguardando aprovação` (âmbar, botões Rejeitar/**Aprovar**) →
    `aprovado` (verde, gravado em disco) | `rejeitado` (cinza, sem efeito).
- **Card de comando (`bash`):**
  - Cabeçalho: ícone + comando em mono + badge; o **why** sempre visível.
  - Estados: `aguardando aprovação` (Rejeitar/**Rodar**) → `rodando` →
    `concluído` (exit 0 verde / ≠0 vermelho) | `rejeitado`.
  - Saída colapsada por padrão (últimas ~20 linhas visíveis ao expandir).
- **Texto do assistente:** prosa streamando, tipografia do chat.
- **Rodapé de métricas:** infra · modelo · tokens · tempo — mesmo componente
  do chat atual.
- **Composer:** placeholder "Peça uma alteração em {PROJETO}…"; Enter envia.
- Aprovação por teclado: `A`/`R` com o card focado. **Nunca** Enter global
  aprovando — Enter pertence ao composer.

### 7.5 Seletor de inferência no Modo Code

- Mesmo componente unificado do chat, com dois deltas:
  1. Lista **apenas modelos com tool-calling** (ver D6 para o mecanismo).
  2. **Indicador LGPD em destaque permanente** no header — código-fonte indo
     para provedor de nuvem é o caso mais sensível do sistema.
- **Z.ai: exclusão hard no Modo Code**, independentemente da decisão do modo
  chat (roteamento pela China + código-fonte = não).

### 7.6 Copy (fixado)

"Pasta do projeto" · "Vincular pasta do projeto" · "Nova sessão" ·
"Aprovar" / "Rejeitar" / "Rodar" · "Reiniciar sessão" ·
"Peça uma alteração em {projeto}…" · "aguardando aprovação".

## 8. Segurança e LGPD

Princípio: o **draft-not-execute** do ShvIA vira **propose-approve** aqui —
a Anna nunca toca disco nem executa comando sem confirmação humana.

Guardas obrigatórias (v1):

- **Confinamento à pasta:** toda operação de arquivo é canonicalizada e
  precisa prefixar a pasta vinculada; symlink escape é recusado. Confirmar
  se o `anna` já garante isso (F0); senão, é item **obrigatório** da F1.
- **`bash` sempre manual** na v1 — o toggle de auto-aprovação (D4) cobre
  **apenas edições**, nunca comandos.
- `edit_file` em arquivo binário → recusar com erro claro.
- Escrita direta dentro de `.git/` via `edit_file` → recusar (operações git
  só pela tool `git`).
- Rede: o `anna` fala **somente com o gateway** — nenhuma chamada direta a
  provedor de nuvem a partir da máquina do usuário.
- Auditoria: mantém o padrão do gateway (request_id, tokens, metadados).
  **Verificar na F0** se algum log do gateway persiste conteúdo de prompt;
  se sim, garantir que sessões code não gravem conteúdo de arquivos.
- Operacional: não vincular pastas contendo dados pessoais de clientes;
  documentar no onboarding interno do recurso.

## 12. Critérios de aceite

- [ ] Alternar Chat↔Code preserva o estado dos dois modos.
- [ ] Projeto sem pasta mostra "Vincular pasta do projeto"; o vínculo é
      gravado na config local e sobrevive a restart do app.
- [ ] Caminho vinculado inexistente → estado de erro com "Revincular".
- [ ] Primeira mensagem spawna o `anna` na pasta correta; fechar o app,
      trocar de modo ou de projeto **não** deixa `anna` órfão (verificar
      com `ps` no teste).
- [ ] Card de diff: **Aprovar** grava no disco (conferível com `git diff`);
      **Rejeitar** não toca o arquivo.
- [ ] `bash` nunca executa sem clique em **Rodar**; o *why* está sempre
      visível antes da decisão.
- [ ] Auto-aprovar edições (quando ligado) **não** se aplica a comandos.
- [ ] Operação com caminho fora da pasta (ex.: `../`) é recusada e aparece
      como erro na timeline.
- [ ] Rodapé de métricas mostra infra, modelo, tokens e tempo do turno.
- [ ] Seletor no Modo Code lista apenas modelos com tool-calling; Z.ai
      ausente; indicador LGPD visível no header.
- [ ] Crash do `anna` → card de erro + "Reiniciar sessão" retoma o fluxo.
- [ ] Sessão anterior aparece na coluna 2 e é retomável (conforme D5).
- [ ] Versão do app bumpada; cache busters atualizados se CSS/JS mudou.
